# LinkedIn как второй источник вакансий + поиски в БД

Дата: 2026-09-08
Статус: согласовано с пользователем, готово к написанию плана реализации

## Зачем

Сейчас ассистент умеет один источник — Upwork, а поиски заданы строкой в `.env`
(`UPWORK_SEARCH_URLS`) и меняются только правкой файла на сервере с перезапуском.

Нужно:
1. добавить LinkedIn вторым источником вакансий;
2. вынести поисковые запросы обоих источников в БД и сделать их редактируемыми
   через веб-панель.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Доступ к LinkedIn | **Под аккаунтом пользователя** (не гостевой поиск) — риск принят осознанно |
| Где живут поиски | **В БД, оба источника**; `UPWORK_SEARCH_URLS` из `.env` переезжает однократно и больше не используется |
| Что делаем с подходящей LinkedIn-вакансией | **То же, что с Upwork**: скоринг → черновик → Telegram и панель. Промпт генерации свой (сопроводительное письмо ≠ Upwork-proposal) |
| Фильтры | У фильтра появляется **источник** (Upwork / LinkedIn / любой) |
| Доменная модель | **Вариант B**: Upwork-специфичные поля становятся необязательными, добавляется LinkedIn-специфика; несводимое уходит в `linkedin_job_facts` |

## Риски

**Бан аккаунта LinkedIn.** Пользовательское соглашение LinkedIn прямо запрещает
автоматический сбор данных, детект у них агрессивнее, чем у Upwork, и блокировки
аккаунтов реальны и окончательны. Пользователь выбрал работу под своим аккаунтом,
понимая это. Митигации: низкая частота опроса (интервал заведомо больше, чем у
Upwork), джиттер, отдельный часовой лимит загрузок страниц, отдельный circuit
breaker, отдельный kill switch, прокси как штатная настройка. Ни при каких
условиях не автоматизируем подачу отклика — как и на Upwork, отправляет человек.

**Репутация IP.** На Upwork уже воспроизведена проблема: с датацентрового IP
(DigitalOcean) Cloudflare выдаёт таймауты там, где с домашнего IP всё проходит.
У LinkedIn с этим строже. Поэтому `LINKEDIN_PROXY` закладывается сразу, а не
«когда понадобится».

**Дрейф схемы страницы.** Ровно на этом обожглись с Upwork: структура была
заложена вслепую (перехват сетевого JSON), а реальность оказалась другой
(SSR-состояние в `window.__NUXT__`), и адаптер переписывался. Отсюда жёсткое
правило ниже: сначала разведка и фикстуры, потом код.

## Доменная модель

Изменения в `domain/models.py`.

### Новые перечисления

```python
class JobSourceName(StrEnum):
    UPWORK = "upwork"
    LINKEDIN = "linkedin"

class WorkplaceType(StrEnum):      # LinkedIn
    REMOTE = "remote"
    HYBRID = "hybrid"
    ONSITE = "onsite"

class EmploymentType(StrEnum):     # LinkedIn
    FULL_TIME = "full_time"
    PART_TIME = "part_time"
    CONTRACT = "contract"
    TEMPORARY = "temporary"
    INTERNSHIP = "internship"

class SalaryPeriod(StrEnum):       # LinkedIn
    YEAR = "year"
    MONTH = "month"
    HOUR = "hour"
```

Новый value-объект рядом с существующими `Money`/`RateRange` (тоже frozen):

```python
class SalaryRange(BaseModel):      # LinkedIn
    min_amount: Decimal | None
    max_amount: Decimal | None
    currency: str
    period: SalaryPeriod
```

Отдельно от `RateRange`, потому что `RateRange` семантически почасовая ставка
Upwork, а у LinkedIn вилка чаще годовая и приходит с явным периодом.

### `JobPosting`

Добавляется:

- `source: JobSourceName` — обязательное, определяет, какие поля осмысленны;
- `employment_type: EmploymentType | None` — LinkedIn;
- `workplace_type: WorkplaceType | None` — LinkedIn;
- `salary_range: SalaryRange | None` — LinkedIn (`min`, `max`, `currency`, `period`);
- `applicants_count: int | None` — LinkedIn;
- `seniority: str | None` — LinkedIn (строкой: их градация не совпадает с нашей `ExperienceLevel`).

Становится необязательным (сейчас обязательное или с дефолтом):

- `job_type: JobType | None` — это **модель оплаты Upwork** (фикс/почасовая), у
  LinkedIn такого измерения нет. Специально не смешиваем с `employment_type`:
  это разные оси, и фильтр «job_type = fixed» не должен ничего значить для
  LinkedIn;
- `competition: ProposalTier | None` — тир откликов Upwork. LinkedIn-эквивалент —
  отдельное поле `applicants_count`. **Намеренно не сводим их в одно поле**:
  «27 откликов на LinkedIn» и «20–50 proposals на Upwork» — несопоставимые
  величины, единое поле создало бы ложную эквивалентность;
- `entry_cost: int | None` — Connects, только Upwork.

### `ClientProfile`

Смысл расширяется с «заказчик Upwork» до «кто нанимает». Поля:

- `name: str | None` — новое; компания на LinkedIn. Upwork имя заказчика в выдаче
  поиска не отдаёт → `None`;
- `country: str | None` — оба источника;
- `payment_verified: bool | None` — только Upwork (было `bool = False`);
- `total_spend: Decimal | None` — только Upwork (было `Decimal(0)`);
- `hire_rate: float | None` — только Upwork (уже необязательное);
- `avg_rating: float | None` — только Upwork (уже необязательное);
- `reviews_count: int | None` — только Upwork (было `int = 0`).

**Почему именно `None`, а не дефолты.** Движок фильтров (`domain/filters.py`,
Фаза 1) уже реализует правильную семантику отсутствующего поля: включающее
правило (`eq`, `gte`, `contains`, ...) на `None` не проходит, исключающее (`ne`,
`not_in`, `not_contains`) — проходит. То есть честные `None` бесплатно встают в
существующую механику, а дефолт `payment_verified = False` для LinkedIn был бы
выдуманным значением, на которое среагировали бы и фильтры, и промпт скоринга.

### Фильтры

`domain/filters.py`:

- в `FilterField` добавляются: `source`, `company_name`, `employment_type`,
  `workplace_type`, `salary_min`, `salary_max`, `applicants_count`, `seniority`;
- в `FilterSet` добавляется `source: JobSourceName | None` (`None` = применять ко
  всем источникам). `filter_service.matches_any` пропускает пресет, если его
  `source` задан и не совпадает с `job.source`.

## Схема БД и миграции

SQLite не умеет менять ограничения колонок напрямую — все три миграции пишутся
через `op.batch_alter_table` (пересоздание таблицы), как того требует Alembic для
SQLite.

**`0004_multi_source`**
- `job_postings.source` — новая колонка; существующие строки заполняются
  `'upwork'`;
- уникальность переезжает с `external_id` на пару `(source, external_id)`:
  идентификаторы LinkedIn тоже числовые, и теоретическое пересечение с Upwork
  реально;
- новые nullable-колонки: `company_name`, `employment_type`, `workplace_type`,
  `salary_min`, `salary_max`, `salary_currency`, `salary_period`,
  `applicants_count`, `seniority`;
- становятся nullable: `job_type`, `competition`, `entry_cost`,
  `client_payment_verified`, `client_total_spend`, `client_reviews_count`.

**`0005_search_queries`**
- таблица `search_queries`: `id`, `source`, `name` (уникально в паре с `source`),
  `query` (URL или строка запроса), `is_active`, `created_at`, `updated_at`.

**`0006_linkedin_job_facts`**
- таблица `linkedin_job_facts` — зеркало `upwork_job_facts`: `job_external_id`
  (уникально), `raw_payload` (JSON), `created_at`, `updated_at`. Материал для
  реплея маппера при дрейфе схемы.

**`0007_filter_source`**
- `filter_sets.source` — nullable колонка.

### Перенос `UPWORK_SEARCH_URLS`

Не миграцией данных, а разовым засевом при старте приложения: если таблица
`search_queries` пуста и в `.env` задан `UPWORK_SEARCH_URLS` — импортировать его
значения одной записью на URL. Так поведение предсказуемо, тестируемо и не
зависит от того, читают ли миграции настройки. После переноса переменная в
`.env`/`.env.example` помечается как устаревшая (оставляем ради миграции старых
установок, в коде не используется).

## Адаптер LinkedIn

Структура `adapters/linkedin/` зеркалит `adapters/upwork/`: `browser.py`,
`auth.py`, `payload_models.py`, `mapper.py`, `source.py`, `dom_fallback.py`.
Свой каталог persistent-профиля (`LINKEDIN_PROFILE_DIR`), отдельный от Upwork.

**Порядок работ жёсткий: сначала разведка, потом код.** Payload-модели и маппер
пишутся только против реально захваченных фикстур, сохранённых в
`tests/fixtures/linkedin/`. Это прямое следствие того, как пошло на Upwork:
угаданная заранее структура оказалась неверной и была переписана целиком, а
работать начало ровно после того, как маппер стали писать по фактическим данным.
До разведки в плане не должно быть ни одной строчки про конкретные селекторы или
поля.

Вход: `tools/linkedin_login.py` по образцу уже отлаженного `tools/login.py` —
headful-окно локально, человек входит сам (включая любые проверки), профиль
сохраняется на диск и переносится на сервер файлами. Сервер сам не логинится.

## Конфигурация поисков через веб

**API** (`api/routes/searches.py`): `GET /searches` (список, опционально
`?source=`), `PUT /searches/{source}/{name}` (создать/заменить), `DELETE
/searches/{source}/{name}`.

**Панель**: раздел «Поиски» рядом с «Фильтрами» — таблица (источник, имя, запрос,
активен, кнопки «Изменить»/«Удалить») и форма создания/правки с выпадашкой
источника. Пользователь вставляет URL сохранённого поиска целиком, как сейчас
делает в `.env`.

**Чтение в рантайме**: `UpworkJobSource`/`LinkedInJobSource` получают список
активных поисков своего источника из БД на каждый цикл — по тому же принципу, что
и фильтры (перечитываются каждый цикл, правка через панель применяется со
следующего цикла без перезапуска).

## Изоляция источников

У каждого источника своя `PollingPolicy` (свой часовой лимит загрузок, свой
circuit breaker, свой интервал) и свой `PollingRunner` с собственным id задачи в
планировщике. Блокировка LinkedIn не должна останавливать Upwork и наоборот.

`IngestService` инстанцируется по одному на источник; пайплайн, дедуп, скоринг,
генерация и уведомления — общие.

**Admin API** становится пер-источниковым: `GET /admin/status` возвращает
состояние по каждому источнику; `POST /admin/pause` и `/admin/resume` принимают
`?source=` (без параметра — применить ко всем). Панель показывает по индикатору и
паре кнопок на источник.

## Что меняется в уже работающем

- **Промпты** (`adapters/llm/prompts.py`): отдельный системный промпт генерации
  для LinkedIn (сопроводительное письмо), выбор по `job.source` в
  `ProposalService`. Промпт скоринга общий, но в описание вакансии подставляются
  только осмысленные для источника поля.
- **Telegram** (`adapters/telegram/formatting.py`): в карточке появляется
  источник; блоки про заказчика/бюджет рендерятся только когда значения есть.
- **Панель**: колонка «Источник» в таблице вакансий, фильтр по источнику,
  выпадашка источника в форме фильтра, раздел «Поиски», пер-источниковый kill
  switch.
- **Конфигурация**: новые переменные `LINKEDIN_ENABLED`, `LINKEDIN_EMAIL`,
  `LINKEDIN_PASSWORD`, `LINKEDIN_PROFILE_DIR`, `LINKEDIN_HEADLESS`,
  `LINKEDIN_PROXY`, `LINKEDIN_POLL_INTERVAL_MINUTES`,
  `LINKEDIN_MAX_PAGE_LOADS_PER_HOUR`, `LINKEDIN_MAX_PAGES_PER_SEARCH`.
  `.env` и `.env.example` держатся структурно идентичными (правило проекта).
- **Тесты**: существующие правятся под новую модель (обязательный `source`,
  необязательные Upwork-поля); добавляются тесты маппера LinkedIn на реальных
  фикстурах, тесты пер-источниковой изоляции и CRUD поисков.

## Фазы и критерии готовности

**Фаза L1 — разведка LinkedIn.** Живой прогон под аккаунтом пользователя,
сохранение фикстур страницы поиска в `tests/fixtures/linkedin/`, описание
фактической структуры данных.
*Готово когда:* фикстуры лежат в репозитории, структура задокументирована, ни
одной догадки о полях не осталось.

**Фаза L2 — доменная модель и миграции.** Изменения `domain/models.py`,
`domain/filters.py`, схемы БД, миграции `0004`–`0007`, правка существующих тестов.
*Готово когда:* ruff/mypy/pytest зелёные, миграции накатываются на копию боевой
БД, существующие Upwork-вакансии читаются без потерь.

**Фаза L3 — адаптер LinkedIn.** Payload-модели и маппер против фикстур,
`tools/linkedin_login.py`, `LinkedInJobSource`, `linkedin_job_facts`.
*Готово когда:* маппер разбирает реальные фикстуры офлайн-тестами; локальный вход
сеет профиль; один живой цикл возвращает вакансии.

**Фаза L4 — поиски в БД и веб.** Таблица, CRUD-эндпоинты, раздел панели, засев
из `.env`, чтение источниками из БД.
*Готово когда:* поиск создаётся и правится в браузере, применяется со следующего
цикла без перезапуска; старое значение `UPWORK_SEARCH_URLS` перенесено
автоматически.

**Фаза L5 — изоляция источников и промпты.** Пер-источниковые policy/runner/admin
API, промпт сопроводительного письма, источник в Telegram и панели.
*Готово когда:* блокировка одного источника не останавливает второй (проверяется
тестом на circuit breaker); LinkedIn-вакансия проходит весь путь до черновика в
Telegram с правильным промптом.

## Вне объёма

- Автоматическая подача откликов и LinkedIn Easy Apply — никогда, по той же
  причине, что и на Upwork: отправляет человек.
- LinkedIn Recruiter, InMail, обогащение данными страницы компании.
- Гостевой (без логина) режим сбора — решение принято в пользу работы под
  аккаунтом; при необходимости это отдельная задача.
- Connects/`entry_cost` для Upwork со страницы вакансии — остаётся известным
  пробелом текущей реализации, к LinkedIn отношения не имеет.
